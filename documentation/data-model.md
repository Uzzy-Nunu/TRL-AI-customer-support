# Supabase Data Model

## Design principles

- Store support data separately from brand knowledge and application configuration.
- Use UUID primary keys and UTC timestamps.
- Keep AI output structured so it can be filtered and rendered safely.
- Enforce customer ownership with Row Level Security.
- Store only the minimum personal data required for support.

## `support_requests`

| Column | Type | Rules |
|---|---|---|
| `id` | `uuid` | Primary key, generated by database |
| `user_id` | `uuid` | References `auth.users`, nullable only for an explicitly supported guest flow |
| `name` | `text` | Required, 2–100 characters |
| `email` | `citext` or `text` | Required, normalized before storage |
| `subject` | `text` | Required, 3–160 characters |
| `complaint` | `text` | Required, 10–5,000 characters |
| `customer_category` | `text` | Optional user-selected hint |
| `category` | `text` | AI/server result enum |
| `urgency` | `text` | `LOW`, `NORMAL`, or `HIGH` |
| `summary` | `text` | AI result, maximum 300 characters |
| `ai_response` | `text` | Validated customer-facing response |
| `safe_next_step` | `text` | Validated next step |
| `needs_escalation` | `boolean` | Defaults to false |
| `status` | `text` | `PENDING`, `AI_RESPONDED`, or `RESOLVED` |
| `order_reference` | `text` | Optional non-sensitive order number |
| `provider_model` | `text` | Optional model identifier |
| `provider_latency_ms` | `integer` | Optional operational metric |
| `failure_code` | `text` | Safe internal code, nullable |
| `created_at` | `timestamptz` | Defaults to `now()` |
| `updated_at` | `timestamptz` | Updated by server/database trigger |
| `resolved_at` | `timestamptz` | Nullable |

Use check constraints for enums and length constraints where practical. Normalize email for lookup but do not use email alone as authorization.

## Optional `support_events`

Use an event table if auditability is needed:

```text
id, request_id, actor_user_id, event_type, metadata_json, created_at
```

Do not store raw provider prompts or secrets in event metadata. Useful event types include `REQUEST_CREATED`, `AI_RESPONDED`, `AI_FAILED`, `RETRY_REQUESTED`, and `RESOLVED`.

## Indexes

Recommended indexes:

- `(user_id, created_at desc)` for the dashboard.
- `(status, updated_at desc)` for future human-support tooling.
- `(category, created_at desc)` for reporting.
- `(email, created_at desc)` only if a controlled guest-support lookup is implemented.

## RLS expectations

Enable RLS on every customer-facing table.

- Authenticated users can `select` requests where `user_id = auth.uid()`.
- Authenticated users can insert only requests whose `user_id` is `auth.uid()`.
- Customers can update only explicitly permitted fields, such as resolving their own request.
- Provider response fields should be written by a trusted server path.
- No public anonymous policy should allow listing or reading arbitrary requests.

If a service-role client is used for server-side updates, pair it with explicit ownership checks in application code. Service-role access bypasses RLS and must never be sent to the browser.

## Retention and deletion

Before production, decide how long complaint text and AI responses are retained, how account deletion affects requests, and whether customers can export/delete support history. This decision should be reflected in a migration, privacy notice, and operational runbook.
